# Troubleshooting

Symptom → likely cause → what to check → fix, for every area of the system.
The messages quoted are the ones the BFF or the console actually emit, so the
table can be searched for the text on screen.

## Upstream connections (MILS, Concore)

| Symptom                                                           | Likely cause                                                                                | Check                                                                            | Fix                                                                                       |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| MILS card red; _Save & test_ fails on `GET /Countries` with `401` | No usable token: no stored signing key, empty `MILS_JWT`, nothing forwarded                 | `hasSigningKey` on `/integrations/mils`; test result `source`                    | Paste the RS256 key (+ passphrase for an encrypted PEM) or run `load:signing-key`         |
| Signing key saved but MILS still answers `401`                    | Wrong claims (`iss`/`sub`/`aud`/`kid`) or the key does not match the certificate MILS knows | Fingerprint shown on the panel vs the certificate                                | Set the JWT claim fields on the MILS panel to what MILS expects                           |
| Concore card red; test reports `authSource: none`                 | No stored API key and no `CONCORE_TOKEN` / `CONCORE_API_KEY` in env                         | `/integrations/concore` test result                                              | Save an API key + organisation id                                                         |
| Concore lists come back empty / for the wrong organisation        | `organisation_id` is injected from the stored org id on allow-listed list reads             | `concoreOrgId` on the panel; the route is in `apps/api/src/concore/org-scope.ts` | Set the right org id, or pass `organisation_id` explicitly — an inbound value always wins |
| Settings change has no effect                                     | Console pointed at a different BFF origin                                                   | The API-origin value in the console (localStorage) vs `VITE_API_BASE_URL`        | Fix the origin; in Docker the web image bakes it at build time — rebuild                  |
| Dashboard shows a zeroed section and a red connection pill        | That upstream is unreachable; collectors zero their section instead of failing the page     | The pill reuses the same test as the Integrations page                           | Fix the connection; the section fills on the next 30 s refresh                            |

## Console sessions

| Symptom                                                          | Likely cause                                                                          | Check                       | Fix                                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------- |
| `Account temporarily locked due to repeated failed logins.`      | `AUTH_LOGIN_MAX_ATTEMPTS` (5) exceeded                                                | `lockedUntil` on the user   | Wait `AUTH_LOCKOUT_MINUTES` (15), or `user:reset-password -- --email=…` clears it |
| Lost the only admin password                                     | In-app reset needs another active admin                                               | —                           | `pnpm --filter @bridge/api user:reset-password -- --email=…` on the host          |
| Signed out after a browser restart / cookie not set behind HTTPS | `NODE_ENV=production` marks the cookie `secure`; served over plain HTTP it is dropped | The scheme the browser uses | Serve over HTTPS (production) or unset `NODE_ENV` locally                         |
| Cross-origin console gets `401` on every call                    | `WEB_ORIGIN` does not include the console's origin, so CORS drops the cookie          | `WEB_ORIGIN` in the api env | Add the origin to the comma-separated list                                        |
| `403` toast: "Ask an administrator to make this change."         | Route requires `ADMIN` (access writes, users, actor registry)                         | Your role under _Account_   | Have an admin do it or change the role                                            |

## Google Drive

| Symptom                                           | Likely cause                                                                                                          | Check                                                          | Fix                                                                                                                     |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Connect button says Google Drive is not set up    | No client id / secret / redirect URI resolve                                                                          | `/integrations/google-drive` test → `none`                     | Fill the panel (or `GOOGLE_*` env)                                                                                      |
| `?google=error&reason=redirect_uri_mismatch`      | Redirect URI saved in Settings is not registered on the OAuth client (exact match, scheme + port)                     | Google Cloud Console → OAuth client → authorised redirect URIs | Register `<bff origin>/api/integration/google-drive/oauth/callback` verbatim                                            |
| `?google=error&reason=invalid_state`              | OAuth `state` expired (10 min, `STATE_TTL_MS` in `apps/api/src/google-drive/google-account.service.ts`) or was reused | —                                                              | Start the connect flow again from the console                                                                           |
| Drive calls answer `409` "connection has expired" | Google returned `invalid_grant` — grant revoked, or the OAuth client was changed                                      | Google account → third-party access                            | Reconnect                                                                                                               |
| `410 Gone` on a file's content                    | Blob missing on disk (volume wiped or moved)                                                                          | `files:verify` lists every such row                            | _Re-sync from Drive_ on the element restores it                                                                         |
| `disallowed_useragent` from Google                | Consent screen opened inside the Electron window; Google blocks embedded webviews                                     | Desktop only                                                   | The `window.open` → system-browser path must be working; see `desktop.md` |
| Download refused as too large                     | File exceeds `FILE_STORE_MAX_BYTES` (200 MiB)                                                                         | File size in Drive                                             | Raise the limit or skip the file                                                                                        |

## API Explorer

| Symptom                                                                                | Likely cause                                                                                                       | Check                                             | Fix                                                                             |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Scalar shows `403 … is not under this API's base URL`                                  | The operation's server (or a URL you typed) is outside the API's base URL                                          | API settings → base URL                           | Pick a server under the base URL, or change the base URL                        |
| `403 … points at a local/private host` / `… resolves to a private or loopback address` | The target is loopback / RFC1918 / link-local / `.local`-style, blocked by `TargetGuard`                           | `API_EXPLORER_ALLOW_PRIVATE_TARGETS`              | Set it to `1` (already the desktop default)                                     |
| `401 Authentication required` in Scalar's response pane                                | The console session expired (the proxy needs the cookie)                                                           | —                                                 | Sign in again                                                                   |
| Import says "Not an OpenAPI document"                                                  | The URL returned HTML without a discoverable spec link, or the text has no `openapi` / `swagger` field             | Fetch the URL yourself                            | Point at the raw document                                                       |
| Import times out                                                                       | Document fetch exceeded `API_EXPLORER_IMPORT_TIMEOUT_MS` (15 s)                                                    | —                                                 | Paste the document text, or raise the timeout                                   |
| Register button disabled: "Payload exceeds the store limit"                            | Response (+ request) larger than the 64 KiB `ITEM_PAYLOAD_MAX_BYTES`                                               | Exchange size on the Requests tab                 | Turn off _Include the request_, or accept the response is too large to register |
| Delete API → `409`                                                                     | Registered elements still point at its exchanges                                                                   | Registered elements for the API                   | Archive them first                                                              |
| Requests tab stays empty                                                               | Recording is off for this API, or Scalar bypassed the proxy for a **localhost** target from a cross-origin console | _Capture_ toggle in the API settings; target host | Enable capture; for localhost targets use a same-origin console (desktop)       |
| Proxied request answers `413`                                                          | Body above `API_EXPLORER_MAX_REQUEST_BYTES` (10 MiB)                                                               | —                                                 | Raise the limit                                                                 |
| A `3xx` comes back instead of the followed page                                        | The proxy never follows redirects (`maxRedirects: 0`)                                                              | —                                                 | Call the `Location` target directly                                             |

## Access control and nodes

| Symptom                                                        | Likely cause                                                                                                     | Check                                                          | Fix                                                                                              |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| A node gets `403 Access to this element is blocked by policy.` | `ACCESS_ENFORCEMENT=enforce` and the resolved decision is `BLOCK`                                                | _Access → Elements_ "effective access" for that node + element | Add a rule / node default, or fall back to `shadow` while adjusting                              |
| Rules configured but nothing is blocked                        | Mode is `shadow` (default) — decisions are only recorded                                                         | Mode shown on _Access → Policy_                                | Follow the rollout in [`runbooks.md`](runbooks.md#roll-out-access-enforcement-shadow-to-enforce) |
| A newly synced node cannot authenticate                        | New actors are created **disabled** (fail closed)                                                                | _Access → Nodes_ "API access" switch                           | Enable it                                                                                        |
| Node token rejected although valid                             | Clock skew beyond `ACTOR_JWT_CLOCK_TOLERANCE_SECONDS` (60), or lifetime above `ACTOR_JWT_MAX_TTL_SECONDS`        | Token `iat`/`exp`/`nbf`                                        | Fix the clock / shorten the token, or raise the tolerance                                        |
| _Access → Statistics_ shows no denials                         | By design: that tab covers external reads of the unauthenticated mils-internal surface, where no decision exists | Dashboard `denied7d` and the `[shadow]` log lines              | Look at the dashboard, not the tab                                                               |
| _Access → Nodes_ is empty                                      | Registry never synced                                                                                            | `ActorRegistration` rows                                       | Sync from the console or `sync:actor-registry`                                                   |
| A denial is logged only once although the node keeps polling   | Shadow denials are throttled to one line per node + element per hour                                             | —                                                              | Expected; the metric rows still count every request                                              |

## Peer connections

Every outbound call to a peer is recorded (`PeerExchange`) and every refused
inbound token is recorded (`PeerAuthEvent`), so the first check is always the
record: _Access → Nodes_ → the node's **Diagnostics**, the probe result's
**Show the exchange**, the item page's **What happened**, or from a shell
`pnpm --filter @bridge/api peer:diagnose -- --node <name>` and
`inspect:token -- --recent`. The full procedures are in
[`runbooks.md`](runbooks.md#a-peer-read-fails) and
[`runbooks.md`](runbooks.md#a-peer-node-cannot-authenticate).

| Symptom                                                    | Likely cause                                                                                         | Check                                                                                | Fix                                                                                                                              |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `UNREACHABLE … [DNS]`                                      | `NodeHostName` in MILS does not resolve from the API container                                       | `peer:diagnose` dns line; `nslookup` from inside the container                       | Fix the host name in MILS and sync; or the container's DNS                                                                       |
| `UNREACHABLE … [CONNECT] … nothing listens`                | Their reverse proxy does not forward `/rest`, or the port in `NodeHostName` is wrong                 | The tcp line (`ip:port`); an anonymous GET from `peer:diagnose`                      | Their proxy config ([`deployment.md`](deployment.md#the-peer-path-the-proxy-must-forward) has the Caddy block); the port in MILS |
| `UNREACHABLE … [CONNECT] No route`                         | A firewall or egress rule between the two deployments                                                | Same tcp line from both sides                                                        | Network, not software                                                                                                            |
| `UNREACHABLE … [TLS] CERT_HAS_EXPIRED / SELF_SIGNED…`      | Their certificate is expired, self-signed, or not for that host name                                 | The tls line names subject, issuer, validity and Node's reason                       | Their certificate. TLS verification is never relaxed here; a development peer uses `http://` under `PEER_ALLOW_PRIVATE_TARGETS`  |
| `UNREACHABLE … [TIMEOUT] … phase reached was connect`      | Packets dropped rather than refused                                                                  | Whether tcp connected at all                                                         | Firewall; or raise `PEER_FETCH_TIMEOUT_MS` if the peer is merely slow                                                            |
| `NOT_MILS_INTERNAL` naming a reverse proxy or an HTML page | The host answered, the API did not — a default site, a login page, a Basic-auth challenge            | The response headers (`server`, `www-authenticate`) and the body excerpt             | Their routing for `/rest`                                                                                                        |
| `REFUSED` from **every** peer                              | Our key ≠ the certificate MILS publishes for us; issuer drift; our actor not published; expired cert | **This node** self-check — the failing finding names both sides                      | Load the matching key (`load:signing-key`), fix `iss` in Settings, publish/sync the actor in MILS                                |
| `REFUSED` from **one** peer, self-check green              | They have not synced our actor; they read `aud` as the recipient's; their posture pins an audience   | The body excerpt (`"Invalid actor token."` = a bridge refused it); hand over a token | Their operator pastes the handed-over token into their inspector                                                                 |
| A peer says we refuse **them**                             | See the inbound side                                                                                 | Their node's **Diagnostics → What they sent**; `inspect:token --recent`              | The reason is recorded with the request — follow it; only a signature failure needs their token                                  |
| Nothing in **Diagnostics** although calls happened         | `PEER_TRACE=off`, or the rows aged out (31 days / `PEER_TRACE_RETENTION_PER_NODE`)                   | The boot line `Peer federation … · trace …`; `LOG_LEVEL`                             | Turn tracing on; the `HTTP:Peer` log line is written regardless                                                                  |

## mils-internal and payloads

| Symptom                                                                | Likely cause                                                                          | Check                             | Fix                                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------- |
| `GET /rest/MilsItems/{id}/ItemData` → `404`                            | No `MilsItemPayload` row for that MILS item (registered before payloads were written) | _Item payloads_ in the console    | `backfill:item-payloads`, or write the payload manually via `/api/integration/item-payloads` |
| `…/ItemFile` → `410`                                                   | Registered file's blob is missing on disk                                             | `files:verify`                    | _Re-sync from Drive_                                                                         |
| Registration says `REGISTERED` but `payloadStored` is false in the log | Storing the payload is best-effort and failed (e.g. above `ITEM_PAYLOAD_MAX_BYTES`)   | The SUCCESS `RegistrationLog` row | Store it manually via the item-payloads route                                                |
