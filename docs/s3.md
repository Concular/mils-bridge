# Amazon S3 — register files that live in S3 buckets

The S3 source registers objects from **Amazon S3**, or from an S3-compatible
store (MinIO, Cloudflare R2, Wasabi, Ceph RGW, Backblaze B2), into MILS, one
object at a time, or a whole folder at once. Design and phasing:
`plans/s3-integration-plan.md`.

**Status:** all three phases are built. The BFF and CLI come first, then the
console (the connection editor on the Integrations page and on `/s3`, and the
bucket browser under Data explorer → Amazon S3), then folder registration
through the bulk-import runner.

## In the console

- **`/s3`** (Data explorer → Amazon S3 → Buckets) lists the connections: where
  each points, its credential hint, the last test, and how many objects were
  registered through it. The Integrations page shows the same table. Anyone
  signed in may browse and test. Add, edit and delete are ADMIN-only.
- **`/s3/:connectionId?prefix=`** browses one folder level: sub-folders first,
  then objects with their MILS status. A _not registrable_ badge's tooltip says
  why (too large, archived). S3 has no search, so a "go to prefix" box stands
  in for one, and pages come by continuation token ("Load more").
- **Register this folder** (below the listing): one MILS Item per object in the
  folder, sub-folders included unless unticked, all under one Object and
  ItemType. Progress is polled on the card, which offers cancel, retry of
  failed rows and a `results.csv` download.
- **`/s3/:connectionId/object?key=`** shows one object: what S3 says (a HEAD),
  the register form or links to the item and mapping, and the stored copy with
  **Re-sync**. The button turns primary when the object has a new ETag or
  VersionId.

## How it fits together

```
admin ──POST connections──▶ S3Connection (bucket · prefix · region/endpoint · sealed key)
console ─GET objects?prefix=─▶ ListObjectsV2 (Delimiter "/")  ─▶ folders + objects + mapping state
console ─POST registrations──▶ HeadObject → GetObject (pinned version) → file store (sha256)
                                → POST /Items to MILS → ResourceMapping (s3-object) → ItemData = StoredFileDto
```

**The bytes are copied, never referenced.** A registered object is downloaded
into the local file store before the MILS Item is created, exactly as a
Google Drive file is. From there it behaves like every other stored file:

- `ItemFile`, `BinaryData`, `/api/integration/files/:milsId/content` and
  `PropertyData`'s `MilsBinaryDataMediaType` all serve it;
- the peer panel's file button, Access → Elements, the object handshake and
  `GET /rest/MilsItems` all work, because they read `ResourceMapping` /
  `StoredFile`, not S3.

The unauthenticated `/rest/*` reads therefore never call S3, and no presigned
URL ever leaves the BFF. A changed object reaches MILS only through an explicit
**re-sync**.

**Identity.** An object is identified by its canonical URI:

- `s3://<bucket>/<key>` against AWS, where bucket names are global;
- `s3+<endpoint-host>://<bucket>/<key>` against a custom endpoint, where they
  are not.

The URI is the mapping's `concoreId` (kind `s3-object`) and
`StoredFile.sourceFileId`. A connection is only the way in, so two connections
to one bucket cannot register an object twice. One object is one element:
registering it again answers `EXISTS`, or retries a `FAILED` row.

## Connections

A connection is one bucket, an optional **prefix** that confines it, and one
credential. Connections belong to the node and are managed by admins: creating,
editing and deleting them needs `ADMIN`, while browsing and registering need a
console session. There can be several, for example two teams with two buckets,
or one bucket split by prefix.

| Field            | Notes                                                                                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| `bucket`         | S3 naming rules: 3–63 characters, lowercase letters, digits, `.`, `-`                                                 |
| `region`         | An AWS region (`eu-central-1`), or whatever the custom store wants (`auto` for R2)                                    |
| `endpoint`       | Empty = AWS. An absolute http(s) URL for an S3-compatible store                                                       |
| `forcePathStyle` | Defaults to on when an endpoint is set (MinIO and most stores need it)                                                |
| `prefix`         | Normalised to `''` or `…/`. Keys outside it answer **404**, both browsing and registering                             |
| `authType`       | `access-key` (id + secret, optional STS `sessionToken`) or `default-chain` (only with `S3_ALLOW_DEFAULT_CREDENTIALS`) |

The secret access key and the session token are write-only. They are sealed
with `SECRETS_KEY` when it is set, never returned (the DTO shows
`hasSecretAccessKey` and an `AKIA…WXYZ` hint), and never logged. On `PATCH`,
an omitted secret keeps the stored one and `''` removes it. Every write leaves
an `AuditEvent` (kind `SETTINGS`) naming the changed fields.

Deleting a connection keeps its registered files. The stored copy, the mapping
and the MILS item stay, and `StoredFile.s3ConnectionId` becomes null.
Re-syncing such a file needs another connection to the same bucket, named
explicitly.

### S3-compatible stores

| Store         | `endpoint`                                      | `region`              | Path style |
| ------------- | ----------------------------------------------- | --------------------- | ---------- |
| MinIO         | `https://minio.example.com`                     | `us-east-1`           | on         |
| Cloudflare R2 | `https://<account-id>.r2.cloudflarestorage.com` | `auto`                | on         |
| Wasabi        | `https://s3.<region>.wasabisys.com`             | e.g. `eu-central-1`   | on         |
| Backblaze B2  | `https://s3.<region>.backblazeb2.com`           | e.g. `eu-central-003` | on         |

A store on loopback or a private network (a local MinIO) needs
`S3_ALLOW_PRIVATE_ENDPOINTS=1`, which also allows plain `http`.

### Least-privilege IAM policy

The BFF only ever calls `ListObjectsV2`, `HeadObject`, `GetObject` and
`HeadBucket`, and it never writes:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::BUCKET",
      "Condition": { "StringLike": { "s3:prefix": ["PREFIX*"] } }
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion"],
      "Resource": "arn:aws:s3:::BUCKET/PREFIX*"
    }
  ]
}
```

Add `kms:Decrypt` on the key for SSE-KMS buckets. A prefix-scoped policy makes
`HeadBucket` answer 403. The connection test treats that as working, as long as
the one-key list under the prefix succeeds.

## Endpoints

All of them are under `/api/integration/s3/*` and need a console session. None
is in `PUBLIC_INTEGRATION_PREFIXES`.

| Method + path                                                      | Guard   | Does                                                                                             |
| ------------------------------------------------------------------ | ------- | ------------------------------------------------------------------------------------------------ |
| `GET connections` · `GET connections/:id`                          | session | Redacted connection(s), with `registeredCount` and the last test                                 |
| `POST connections`                                                 | `ADMIN` | Create (`s3ConnectionInputSchema`)                                                               |
| `PATCH connections/:id`                                            | `ADMIN` | Edit. A moved destination or credential clears the last test                                     |
| `DELETE connections/:id`                                           | `ADMIN` | Delete. Registered files survive                                                                 |
| `POST connections/:id/test`                                        | session | `HeadBucket` + one-key list under the prefix. The result is stored on the row                    |
| `GET connections/:id/objects?prefix=&continuationToken=&pageSize=` | session | One folder level: `folders`, `objects` (with `registrable` and mapping state), breadcrumb `path` |
| `GET connections/:id/object?key=`                                  | session | `HeadObject` + mapping + stored copy + `isStale` (the key holds `/`, so it is a query parameter) |
| `POST registrations`                                               | session | `{ connectionId, key, milsObjectId, itemTypeId, parentMappingId? }`                              |
| `POST registrations/resync`                                        | session | `{ sourceUri, connectionId? }` → `unchanged` / `updated` / `restored`                            |

Folder registration is a bulk import:
`POST /api/integration/bulk-imports/s3` with
`{ connectionId, prefix, recursive, milsObjectId, itemTypeId, start }`. It lists
the prefix into rows (one per object; folder markers left out; objects that can
never be registered become INVALID rows), and the bulk-import runner registers
each one with the same call as the single-object route. Above
`BULK_IMPORT_MAX_ROWS` objects the import is refused, never truncated. Progress,
cancel, retry, the rows and `results.csv` are the ordinary
`/bulk-imports/:id/*` routes ([Bulk import](bulk-import.md)).

Keys and prefixes in requests are **relative to the connection's prefix**. The
browser names a connection id and a key, never a bucket, an endpoint or a
credential, so nothing in a request chooses where the BFF connects.

## Registration rules

`HeadObject` runs first. These cases are refused before anything is written:

| Case                                                                            | Answer                        |
| ------------------------------------------------------------------------------- | ----------------------------- |
| A folder marker (key ends in `/`, 0 bytes)                                      | `400`                         |
| Larger than `FILE_STORE_MAX_BYTES`                                              | `413`                         |
| `GLACIER` / `DEEP_ARCHIVE` not restored, or an Intelligent-Tiering archive tier | `409`, restore it in S3 first |
| Missing key, or a key outside the prefix                                        | `404`                         |

The download is pinned to the `VersionId` the HEAD saw, so the recorded ETag
and version describe the stored bytes. It runs under a total deadline
(`S3_DOWNLOAD_TIMEOUT_MS`), and the store's streaming cap applies even if
`Content-Length` lied. The mime type is **sniffed from the bytes**
(`mime-choice.ts`, as for uploads). S3's `Content-Type` is set by the uploader,
is often `binary/octet-stream`, and is kept only as `sourceMimeType`.

**Re-sync** compares the object's current ETag and VersionId with the stored
ones. It re-downloads when they differ or when the blob is missing on disk,
refreshes the ItemData descriptor, and writes an `UPDATE` registration log
row. The MILS item is never touched. `s3:resync` does the same in batch.

## Errors

S3 failures are phrased by `classifyS3Error()` (`s3/s3-errors.ts`). Each one
names a fix:

| S3 says                                              | The BFF says                                                   |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| `AccessDenied` / `Forbidden`                         | the credential may not read `s3://bucket` — see the IAM policy |
| `InvalidAccessKeyId` / `SignatureDoesNotMatch`       | the access key id / the secret is wrong                        |
| `ExpiredToken`                                       | paste fresh temporary credentials                              |
| `PermanentRedirect` / `AuthorizationHeaderMalformed` | the bucket is in `<region>`, not `<configured>`                |
| `NoSuchBucket` / bucket `NotFound`                   | check the bucket name and the endpoint                         |
| `InvalidObjectState`                                 | the object is archived — restore it first                      |
| `ENOTFOUND` / `ECONNREFUSED` / TLS codes             | the endpoint does not resolve / refused / bad certificate      |

## Configuration

| Env                            | Default                                  | Meaning                                                                                                     |
| ------------------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `S3_ALLOW_DEFAULT_CREDENTIALS` | off                                      | Lets `default-chain` connections use the host's AWS identity (env, shared config, instance/task role, IRSA) |
| `S3_ALLOW_PRIVATE_ENDPOINTS`   | off                                      | Lets a custom endpoint be loopback/private and plain `http`. The desktop needs it for a local MinIO         |
| `S3_REQUEST_TIMEOUT_MS`        | 15 s                                     | Connect and socket-inactivity timeout                                                                       |
| `S3_DOWNLOAD_TIMEOUT_MS`       | `FILE_STORE_DOWNLOAD_TIMEOUT_MS` (120 s) | Total deadline on one download                                                                              |

Both switches are env rather than settings on purpose: each one widens what an
ADMIN can make the server reach. They are re-checked every time a connection is
used, so turning one off takes effect without editing any row.

## CLI

- `register:s3-object -- --connection <name|id> --key <key> --object '{…}' --item-type '{…}'`
  registers one object. `--list [--prefix a/]` lists one level instead. It boots
  `AppModule`, so it is also the cheapest DI check of the module.
- `s3:resync [--connection <name|id>] [--apply]` makes one `HeadObject` per
  registered file and reports what moved. `--apply` re-downloads.
- `encrypt:secrets` covers `S3Connection.secretAccessKey` and
  `S3Connection.sessionToken`.
- `files:verify` and `files:gc` need nothing new.

## What is deliberately not here

- Writing to S3 (exporting MILS items to a bucket).
- Event-driven sync (S3 notifications / SQS / EventBridge). Re-sync is a click
  or `s3:resync`.
- SSE-C objects, and triggering Glacier restores.
- Search. S3 has none, so browsing is by prefix.
